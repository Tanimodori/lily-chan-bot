## 写入要求

你的最终产物是本地文件，不是聊天回复。必须按下面四个节点**追加**写入
`outputs/answer.md`，每次写完立即重新读取确认非空：

1. 证据收集完成：写入「## 证据」段落，逐条列出来源（文件:行号 / 日志文件名 / 崩溃片段）。
2. 根因判断完成：写入「## 根因」段落，说明机制而不是只给结论。
3. 修复方案完成：写入「## 修复方案」段落，给出最小改动与影响面。
4. 最终结论完成：写入「## 结论」「## 置信度」「## 建议标签」段落，并同时写入
   `outputs/answer.json`（严格符合 `schemas/answer.schema.json`）。分类按仓库 overlay
   的轴规则填写：类型写在 `issue_type`，其余轴写在 `labels`，类型标签不要重复放进
   `labels`。

补充规则：

- 诊断基于 `code/current`（master）；`code/<tag>` 只用于确认历史版本是否存在问题，
  修复建议不要指向历史版本。
- 接近 55 分钟时停止新的调查，补齐当前结论，并在 `answer.json` 里把 `partial`
  设为 `true`。
- 不要重复读取同一个文件超过 3 次；不要重复执行完全相同的命令。
- 不要修改 `code/` 下的任何文件，不要执行 git push，不要发评论。
- 不要输出任何 token、密钥、环境变量内容。
- `answer.md` 与 `answer.json` 的 Markdown 字段中，代码标识符、路径、配置键、日志关键字、
  版本等使用行内 code；`ai_fix_hint` 保持纯文本，由渲染器放入 `text` 代码块。
